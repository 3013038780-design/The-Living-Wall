# 01 · Git 工作流（Issue → 分支 → PR、rebase）

> 面向碎光 / The Living Wall 的入门笔记。目标：看懂团队在做什么，能跟得上合入节奏，而不是背一堆 Git 命令。

## 一句话地图

```
Issue（要做什么） → 分支（在哪改） → PR（请求合入） → 审查/测试/口头 OK → 合进 main
```

你日常看到的「#5 / #8 / PR#10」大致对应：

| 你看到的 | 它是什么 |
| --- | --- |
| Issue `#5` | 任务单：要解决的问题或功能 |
| 分支 `codex/5-stroke-ripple` | 为这个 Issue 开的改动线 |
| PR `#8` | 把该分支请求合进目标分支的「申请单」 |

编号不必相同：Issue `#5` 对应 PR `#8` 很正常。

---

## 1. Issue：先说清楚「要做什么」

Issue 是协作的起点。碎光里近期例子：

- `#5` FX-01 抚摸涟漪
- `#6` FX-02 局部碎片扰动
- `#7` FX-03 方向性伸展与回弹

好 Issue 通常写清：期望体验、边界（什么不该变）、怎么验收。后面 PR、测试基线都围着它转。

**你需要会的：** 打开 Issue 能说出「这单要交付什么」；合入前对照 Issue 看是否真做完。

---

## 2. 分支：在隔离线上改，不直接碰 main

`main` 是「已认可可运行」的主干。功能改动在**分支**上做，改完再通过 PR 合回去。

碎光近期命名习惯（观察现有 PR）：

```text
codex/<issue号>-<短英文描述>
```

例如：

- `codex/5-stroke-ripple` ← PR `#8`（FX-01）
- `codex/6-local-disturbance` ← PR `#10`（FX-02）

**为什么要分支？** 多人/多 BOT 并行时，互不踩踏；回滚也只动一条线。

---

## 3. PR：请求把分支合进去

Pull Request（PR）= 「请审查，并允许把我的分支合进目标分支」。

### 3.1 目标不一定是 main

碎光 FX 链是**叠 PR**（stacked PRs）：

```text
main
  ↑  PR #8   分支 codex/5-stroke-ripple
  ↑  PR #10  分支 codex/6-local-disturbance   （基于 #8 的分支，不是直接基于 main）
  ↑  PR #11  再叠在 #10 上（方向性伸展）
```

所以「#8 → #10 → #11」不是随便编号，而是**依赖顺序**：底层合入后，上层才站得稳。

### 3.2 PR 里通常有什么

以 FX-01（PR `#8`）为参考，常见块：

- **Related to #N**：绑回 Issue
- **摘要 / Summary**：改了什么、故意没改什么
- **参数表**（若有）：如 `RIPPLE_AMP`、间隔等，方便手测与复盘
- **测试计划**：`npm test` / typecheck / build / 手动手测勾选

测试侧约定（项目共识）：过程证据默认挂在 **GitHub PR 评论**（短视频 + 结论）；动态效果优先短视频；**合入门禁含用户口头 OK**。

**你需要会的：**

1. 看 PR 标题与摘要，知道它对应哪张 Issue。
2. 合入前给出口头 OK（或明确还缺什么）。
3. 不挡当前功能门禁：学习文档落地走单独 PR，不拖住 `#8` 这类功能合入。

---

## 4. rebase：把「我的提交」接到更新后的底座上

### 4.1 用搬家理解

把分支想成一摞纸：

- **merge（合并）**：在两摞纸中间夹一张「合并说明」，历史里留下汇合点。
- **rebase（变基）**：把你的那几张纸**揭起来**，整整齐齐贴到**新底座**最上面。历史看起来更直。

叠 PR 时，底座常在动：例如 `#8` 又推了「调大 AMP」的提交，那以 `#8` 为底座的 `#10` 就需要把自己的提交接到最新底座上——这就是 rebase（或同等的「同步底座」操作）出现的场景。

### 4.2 什么时候会听到 rebase

- 底座分支（如 `codex/5-stroke-ripple`）有了新提交，上层 PR 显示冲突或 behind。
- 想让 PR 提交历史更干净，便于审查。
- CI / 审查要求「先对齐最新底座再测」。

### 4.3 你需要抓住的点（不必先会敲命令）

1. **rebase 改的是「提交相对哪条线」**，不是删掉你的功能。
2. 叠 PR 链上，**先对齐下层，再谈上层合入**。
3. 已分享给别人的分支上做 rebase，需要协调（历史被改写）；团队 BOT 操作时，以工程师说明为准。
4. 冲突 = 同一处两边都改了，需要人决定保留谁；不是 Git「坏了」。

## 5. 碎光日常节奏（对照检查清单）

做功能时：

1. 开 / 认领 Issue，写清验收。
2. 从约定底座拉分支（多数新功能从 `main`；叠在未合入 FX 上则从对应功能分支）。
3. 小步提交，PR 写摘要 + 测试计划。
4. 测试留测前/测后证据（评论里短视频 + 结论）。
5. 等审查与**你的口头 OK**，再合入。
6. 下层合入后，上层 PR 同步底座（必要时 rebase），再继续。

学文档时（本目录）：

1. 学徒导师出 md 草稿。
2. 工程师按 Issue → 分支 → PR 落到 `docs/learning/`。
3. **不挡** 功能 PR（尤其 `#8`）合入。

## 6. 常见混淆

| 说法 | 澄清 |
| --- | --- |
| Issue 号 = PR 号 | 否。`#5` 是 Issue，`#8` 可以是对应 PR。 |
| 开了 PR 就等于已合入 | 否。PR 是申请；合入后才进目标分支。 |
| 基于另一功能分支的 PR 很奇怪 | 叠做时很常见；看清 **base** 是谁。 |
| rebase 会丢掉我的改动 | 正常操作是「挪提交」；真正丢改动通常来自错误解决冲突或强推未协调。 |
| 学习文档和功能改同一 PR | 尽量分开，避免文档讨论拖住功能门禁。 |

## 学习建议

- **先读图与表格，再碰命令。** 命令可以让工程师/工具代劳；你的瓶颈通常是「这条 PR 依赖谁、能不能合」。
- **合入决策用验收语言**：「涟漪可见、停抚结束、不破受惊/休息」比「代码看起来行」更稳。
- 下一篇可选：`02` 涟漪 FX（AMP/GAP）、或 `04` 合入门禁（证据与口头 OK）——与本篇直接衔接。
